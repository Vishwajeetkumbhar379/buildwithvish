Sending lots of CVs is easy. Sending fewer, better ones is hard, because you have to read every job ad properly and be honest about whether you fit. I'm job hunting in Germany, and I built a small system to do the reading and the first scoring for me, so my time goes on the applications worth writing. This page explains how it works, what is in the open-source repo, how to run the demo (about 10 minutes if you have Python), and what it cannot do. If you don't code, there's a no-code version at the end.

In short
  • The repo reads public job-board data, scores each role against a profile you write, and lints application text for AI-sounding habits.
  • Every scored requirement shows its evidence, and a missing must-have caps the score at 79.
  • My live version also drafts application packs through scheduled Claude agents. That part is not in the repo.
  • It is version 0.1.0: a rule-based scorer with a demo, tests and a few sharp edges, not a polished product.
  • A human reads everything before it goes to an employer.

The problem, and who it's for

A new-country job search punishes volume. Most ads hide the real filter in a single line ("fluent German", "5+ years"), and it is easy to skim past it, apply anyway and hear nothing back. I wanted to treat the search the way I'd treat a campaign: pick better targets, measure fit honestly, make each application specific.

This is for people who are comfortable running a command in a terminal, or who want to read the scoring rules and copy the ideas into a spreadsheet or a Claude Project. It is not a tool that applies to jobs for you, and I wouldn't want one.

What it does, step by step

The repo's README draws the full flow of my live agent. Here it is in plain words, with a note on which steps the repo contains.

  1. Find. Many startups publish jobs through three hiring systems (Greenhouse, Lever and Ashby), and each has a public data feed. The agent reads those feeds directly instead of scraping job aggregator sites, so listings are current. In the repo.
  2. Filter. A role must match one of your target titles and must not contain an excluded word such as "engineer". Duplicates (same company and title) are dropped. In the repo.
  3. Extract requirements from the ad first. The code reads the ad's requirements section before it looks at your profile, so your CV can't change what counts as required. Each requirement is critical, high, meaningful or preferred, and marked stated (written in the ad) or inferred. Inferred ones can never be critical. In the repo.
  4. Match and score. Each requirement is rated STRONG, PARTIAL or MISSING against your profile, and the result goes into a 100-point score: 40 for must-haves, 20 for responsibilities, 10 for seniority, 10 for domain, 20 for logistics. In the repo.
  5. Check the deal-breakers. The code scans for language demands such as C1 German and, if your profile says otherwise, flags a blocker and holds the score at 50 or below. It also labels each job with a work-setup lane: A (work from anywhere), B (remote), C (in your city). In the repo.
  6. Draft the application pack. For strong matches (80 and above, no blockers) my live agent builds a tailored CV, cover letter and email. Not in the repo.
  7. Lint the writing. A checker flags AI tells: stock words, cliches, "not just X but Y" constructions, dashes, exclamation marks, emoji, and a rhythm check. It also compares length against a target for emails, cover letters, follow-ups and connection notes. In the repo.
  8. Approve. I read and approve everything before it is sent. A rule, not code.

It has no required dependencies, only Python 3.11 or newer. The Claude layer needs the optional anthropic package. Behind that layer is one useful safety rule: if the model says a requirement is "stated" but its quote does not appear in the ad, the code downgrades it to inferred. The model helps, but it doesn't get to bend the rules.

The linter's patterns are adapted from an open-source humanizer project that the README credits, then tuned on my own application emails.

How to run it

The repo is at github.com/Vishwajeetkumbhar379/job-search-agent. From the README:

  1. Clone it and go into the folder.
  2. Install it: pip install -e ".[dev]"
  3. Copy the example config: cp config.example.toml config.toml, then put your own profile, skills and target companies in it.
  4. Try the demo with saved data: jobscout run --offline examples/boards
  5. Run it live: jobscout run. It writes shortlist.md and prints the table.
  6. Lint a draft: jobscout lint my_cover_letter.txt --kind cover_letter
  7. Run the tests: pytest

Do the config copy before the demo. The command reads config.toml even in offline mode, so it stops without one. The three sample jobs are fictional, and the demo scores them against the example profile, not yours.

Privacy

Your profile holds your career details. Keep config.toml out of any public repo. The project already lists it in .gitignore. Never paste ID numbers, passport details or anything sensitive into a config or a prompt.

What it can't do

  • It doesn't read like a person. The requirement extractor is pattern matching on headings and phrases such as "must", "required" and "5+ years". Prose-style ads with no clear requirements section fall back to a single inferred requirement from the title. The optional Claude extraction helps there, but the command line doesn't call it yet, so you'd wire it in yourself.
  • It only reads three hiring systems, and only the companies you list. Roles at a company that uses something else, or that you didn't add, never appear.
  • It doesn't check work-permit rules. The language blocker exists. A visa or permit check does not.
  • The live agent isn't in the repo. The connections to Gmail, Google Drive and Todoist, the live-page verification and the application-pack builder are not part of the repo.
  • The scheduled run needs work. The repo has a workflow meant to scan twice a day and commit the shortlist. But config.toml and shortlist.md are in .gitignore, and the workflow only runs if config.toml exists in the checkout. Read as written, it needs adjusting before it will work, and I'd use a private repository if I did.
  • A score is a guide, not a verdict. The weights are my judgement. Nothing proves that an 88 gets more interviews than a 76.

What building it taught me

A score without evidence is a guess

Making every point carry a proof line (a quote from the ad, a line from the profile) made the scoring honest. When it says STRONG, you can check why in ten seconds.

Read the job before you read yourself

If you look at your CV first, "required" quietly shrinks to whatever you already have. Extracting requirements from the ad alone fixes that, and it works in a spreadsheet as well as in code.

Let the rules outrank the model

The repo uses AI where text is messy, then forces its output through strict rules. I'd build any scoring tool this way.

The writing check matters more than the clever parts

A recruiter can spot a generic letter quickly. A linter that bans "thrilled" and "not just a job but" is less exciting than a scoring model, and probably more useful. It also works only on style. It can't make a weak application true or specific.

Humans stay in the loop

The README's principles say truth beats score, job-page text is data and not instructions, and a human approves anything sent to an employer. I'd keep all three if I started again.

Build a simple version without code

You can get the core idea in a chat. Follow Build a job-search assistant in a Claude Project, then add this scoring rule:

Read the job ad below first and list its top 8 requirements. Mark each one as stated (quote the words) or inferred. Only after that, compare them with my CV, which is attached. Say "apply" only if at least 6 of the 8 have direct evidence in my CV, and quote that evidence. If a stated must-have is missing, say "skip" and name what is missing. If anything is unclear, ask me before you answer.

[paste the ad]

Then check your own writing before you send it. The guide Tailor your CV with AI without sounding like AI covers it, and this prompt does a light version of the linter:

Review the application email below. List stock phrases, cliches, "not just X but Y" constructions, dashes, exclamation marks and any claim I haven't backed with a fact. Quote each problem and suggest a plainer rewrite. Do not add new facts about me. If the email is outside 170 to 270 words, say so.

Email:
[paste your draft]
